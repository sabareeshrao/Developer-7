Comparator defines an external/use-case-specific ordering.\n\nGeoProject has several valid business orderings, so GeoOps keeps the domain object free of one forced Comparable implementation and supplies Comparators where needed.\n\n### ✅ If a Class implements Comparable but a Custom Comparator is supplied while sorting, which ordering takes precedence?\n\nAlready covered.\n\nThe explicitly supplied Comparator controls that sort operation.\n\nSet 38 supplies a Comparator directly, so the delivery rule—not any hypothetical natural order—determines the result.\n\n### ✅ Do you know about the Comparable Interface?\n\nAlready covered.\n\nComparable exposes compareTo(...) for one natural order.\n\nGeoProject intentionally does not implement Comparable because project code, CRS, creation time, and future workflow status could each support different legitimate business views.\n\n### Can you tell me the difference between Comparable and Comparator, and which would you use to sort a list of employees by salary?\n\nComparable puts natural ordering inside the class; Comparator keeps an alternative/business-specific ordering outside the class.\n\nFor employees sorted by salary, Comparator is usually the better answer unless salary truly defines the employee type's one natural ordering.\n\nThe GeoOps equivalent is delivery preparation:\n\n~~~java\nComparator.comparing(GeoProject::coordinateReferenceSystem)\n        .thenComparing(GeoProject::projectCode)\n~~~\n\nThe rule belongs to this report, not to GeoProject identity.\n\n### ✅ Give me a scenario where we should use Comparator.\n\nAlready covered.\n\nSet 38 is the concrete project scenario: delivery preparation needs one deterministic view, while other project features need different orderings.\n\n### You use a custom Comparator for a TreeMap, but some elements are not getting inserted. What might be wrong?\n\nThe Comparator may be returning 0 for distinct keys.\n\nIn TreeMap, comparison determines key uniqueness for the sorted map. If:\n\n~~~text\ncompare(A, B) == 0\n~~~\n\nthe TreeMap treats A and B as the same key position, even if their other fields differ.\n\nThe lesson applies to custom sorting design generally: the Comparator must define the equivalence/tie-breaking behavior intentionally.\n\nGeoOps avoids accidental ties by adding projectCode after CRS:\n\n~~~text\nsame CRS\n→ compare projectCode\n→ deterministic distinct ordering\n~~~\n\n---\n\n## Actual Set 38 behavior\n\nSuppose delivery preparation receives these projects:\n\n~~~text\nTX-HOU-038 / EPSG:4326\nTX-AUS-038 / EPSG:4326\nTX-DAL-038
